## 待修复问题

### R1 · P1：恢复失败可能已经替换正式文件或数据库

- 关联任务：03、08、15、17。
- 位置：`lib/common/task.dart:654–700`、`lib/providers/actions/backup.dart:42–60`。
- 触发条件：导入含同 ID Profile/脚本的备份，而某个节点资产缺失或 SHA-256 不匹配；
  或数据库恢复成功后，节点资产安装、配置反序列化失败。
- 当前行为：`_restoreTask` 在验证节点资产之前把 Profile/脚本复制到正式 home；
  `BackupAction.restore` 又先提交 `database.restore`，随后才安装资产并解析配置。
  节点目录自身有局部回滚，但文件、数据库和设置之间缺少统一提交/回滚。
- 影响：界面报告恢复失败时，旧的有效配置文件或数据库已发生变化，违背 Task 15 的失败保留要求。
- 证据级别：代码路径确认；本轮未执行破坏性真实数据恢复。
- 后续：先在 staging 完成全部数据、配置与资产验证，再协调提交；为失败分支保留完整回滚。
  在现有迁移测试中覆盖坏哈希、资产安装失败、无效配置和旧数据保持。

### R2 · P2：SOCKS4/4a 导出往返丢失版本

- 关联任务：06、14、17。
- 位置：`lib/features/nodes/codec.dart:1887–1890`、`1955–1960`。
- 触发条件：导入 `socks4://USER@HOST:1080#NODE` 或 `socks4a://USER@HOST:1080#NODE`，再导出 URI。
- 当前行为：导入统一存为 `type: socks`，仅用 `version` 保存 4/4a；导出只查看 `type`，忽略 `version`。
- 影响：生成 `socks5://`，再次导入丢失原 SOCKS 版本。当前只验证解析版本的用例未覆盖这个往返路径。
- 证据级别：已用工作区外的 Flutter 临时测试复现；两条版本保持断言均失败，实际输出 scheme 均为 `socks5`。
  这两条复现不计入上面的根包 756 项测试，也未加入业务测试源码。
- 后续：统一版本表示与导出规则，在现有 codec 测试中增加 4/4a 的导入→导出→再导入断言。

### R4 · P2：链路编辑缺少保存前诊断和 warning 确认

- 关联任务：02、11、13、16、17。
- 位置：`lib/views/profiles/chains.dart:318–350`、`lib/providers/actions/setup.dart:318–332`。
- 触发条件：创建包含循环、空/超限分支、不适用于当前绑定 Profile 的节点，或存在兼容性 warning 的链路。
- 当前行为：编辑器显示 hop 数与分支上限，但没有编译后的路径数量/矩阵及诊断；保存操作直接返回 hop。
  实际应用时才阻断 error，warning 只写日志，没有任务契约要求的用户确认。
- 影响：用户可保存随后应用失败的链路，也可能在未看到兼容性提示的情况下应用 warning 配置。
  应用层已有 error 阻断，问题不是完全缺失校验，而是编辑/绑定上下文与确认环节尚未闭合。
- 证据级别：编辑器和配置应用调用路径检查；交互未做设备实测。
- 后续：复用编译器为当前绑定上下文提供预览、路径数量和诊断；全局链保留跨 Profile 复用能力，
  在具体绑定/应用前检查可见性并完成 warning 确认。

### R5 · P1：普通 Rule Profile 缺少链路选用入口，产品闭环待补齐

- 关联任务：00、02、10、13、16、17。
- 位置：`lib/features/chains/runtime.dart:198–205,289–310`、`lib/views/proxies/card.dart:98–114`、
  `core/hub.go:135–168`。
- 触发条件：原配置为 `G.proxies: [Node]`、`rules: [MATCH,G]`，用户绑定链路并设为默认，再在代理页选择生成链组。
- 当前行为：绑定的默认标志只影响聚合组内的排序；组装追加生成 selector，但没有从 `G` 到链组的引用。
  代理页点击只修改被点击 selector 自己的成员选择，`MATCH,G` 的入口保持原样。
- 影响：这个常见 Rule 配置中，绑定/默认/点击生成组仍不使流量进入该链；生成配置存在并不代表链路已被使用。
- 证据级别：调用链核对及临时配置图测试；从规则入口遍历得到 `{G, Node}`，不含生成链 selector。
- 契约说明：Task 13 保留源 Profile 选择是现有明确边界，本问题不是要求隐式覆盖原规则。
  Task 00 的入口语义与该边界之间还缺少用户显式选用链的流程。本结论限定为上述普通 Rule 配置，
  不外推到手工配置链规则或 Global 模式。
- 后续：提供显式接入/选用链入口的操作并保留原 Profile 选择，补绑定、选用、禁用和撤销后的规则入口测试。

### R6 · P2：仅绑定全局链时，其手动节点仍被判为不可见

- 关联任务：02、10、13、16、17。
- 位置：`lib/features/chains/runtime.dart:30–35,390–400,446–450`、`lib/views/profiles/chains.dart:216–223`。
- 触发条件：创建全局手动节点，将其选为链 hop，只把链绑定到 Profile，没有另行绑定节点。
- 当前行为：编辑器允许选择；运行组装的 `visibleNodeIds` 却只纳入当前来源节点和已单独绑定的手动节点，
  最终产生 `invalid-hop` / `empty-chain`，全局组内未绑定成员也会被过滤。
- 影响：用户完成链绑定后仍需额外绑定每个手动节点，当前操作和提示没有明确这个前置条件。
- 证据级别：内存库临时测试复现 `invalid-hop,empty-chain`。
- 后续：明确链绑定是否按依赖纳入手动节点；若保留单独绑定要求，在编辑/绑定时提前检查和提示。
  两种实现均应继续隔离其他 Profile 的来源节点。

### R7 · P2：同名来源节点在运行组装时丢失不同端点

- 关联任务：01、09、10、17。
- 位置：`lib/features/chains/runtime.dart:82–93,109–134`、`lib/features/nodes/service.dart:404–420`。
- 触发条件：同一 Profile 的两个来源节点名字相同，server 等连接参数不同，来源同步以 occurrence 区分保存。
- 当前行为：运行阶段以显示名称建立单值 `profileSourceNodes`，后一个记录覆盖前一个；
  遍历原 `proxies` 时，两个同名入口都取到后一个记录，后续名称分配也找不回被覆盖的端点。
- 影响：最终配置可能出现两份同一 endpoint，而原来的另一个 endpoint 消失，违背重名节点稳定分配要求。
- 证据级别：内存库临时测试输入 `HOST_A` / `HOST_B`，输出 server 集合仅剩 `{HOST_B}`。
- 后续：使用来源稳定键/ID与出现次数建立匹配，再分配运行名称；补同步→组装、重排和 overlay 的同名用例。

### R8 · P2：Core 应用阶段失败时缺少上一份有效状态的恢复

- 关联任务：10、16、17。
- 位置：`lib/providers/actions/setup.dart:446–464`、`core/hub.go:86–92`、`core/common.go:262–278`。
- 触发条件：原始 YAML 预校验通过，但后续 Core 完整解析、Provider 文件或运行初始化发生错误。
- 当前行为：正式配置先原子替换，再调用 `setupConfig`；返回错误时不恢复旧文件，digest 仍是旧值。
  现有 Core 校验入口只解码 Raw 配置，而应用解析失败后会加载默认配置并返回错误。
- 影响：应用报告失败时，磁盘、Core 运行配置和内存 digest 可能分叉；原子写文件只保证单文件替换，
  尚未满足 Task 16 的“错误保留上一份有效配置和运行状态”。
- 证据级别：Dart/Go 调用路径确认；Core 子模块缺失，本轮未运行原生失败注入。
- 后续：补完整预校验与应用失败补偿，覆盖预校验成功但实际加载失败，以及快速连续应用/重启场景。
  该项涉及既有 Core 路径与新配置管线的衔接，不单独归因于本轮新增代码。
